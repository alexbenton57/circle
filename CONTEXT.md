# Circle — Project Context

## 1. Overview

Alex and Matt are developing an evolution of the Circle Gesture System (GCS), with the ambition of entering the Guthman Musical Instrument Competition.

The project explores a musical instrument in which expressive gestures require physical effort. Rather than using a conventional touchscreen controller, the eventual instrument will use a mechanical XY input device with passive physical resistance.

The existing GCS and Circle Gesture Language (CGL) are described in the repository's root `README.md`. The README and existing implementation are the source of truth for established behaviour.

## 2. People and Responsibilities

- **Alex:** Physical instrument design, mechanical engineering, hardware integration and the current Surface prototype.
- **Matt:** Primarily software development, including the CGL and synthesis engine in Max/MSP.

The software and hardware will eventually need to integrate into a single instrument.

## 3. Existing System

The existing GCS consists of:

- MIDI keyboard.
- iPad touchscreen gesture interface.
- Pedals connected to the keyboard.
- Laptop running Max/MSP.

The CGL and Max patch already exist. Their behaviour, parameter definitions and communication interfaces should be reused wherever possible.

Do not assume that the existing implementation matches a proposed redesign. Inspect it.

## 4. Eventual Instrument

The intended instrument is a self-contained unit comprising:

- MIDI keyboard.
- Raspberry Pi running Max/MSP.
- Novel mechanical XY input device.
- Rotary encoders and an MCU for measuring stylus position.
- Passive mechanical resistance, potentially using spring-returned cable spools and magnetic eddy-current brakes.
- Potentially an XY galvanometer projector to display the two-ellipse curve generated by the gesture.
- Additional controls such as knobs, dials and a small display.

### Mechanical input concept

The current concept uses three cable spools arranged around a central stylus. Each spool has a return spring and a damping mechanism. Rotary encoder measurements are used to triangulate the stylus XY position.

The mechanical system is intended to provide passive force feedback. The musician must physically work against the resistance to produce expressive gestures.

These are design intentions, not finalised hardware specifications. Avoid assuming that any particular mechanical implementation is fixed.

## 5. Current Development Stage: Surface Prototype

The `Surface` branch implements an intermediate development platform.

The aim is to use a Microsoft Surface Pro 4 as a substitute for the eventual hardware, allowing the gesture system and physical interaction to be developed independently of the final electronics.

The Surface replaces:

- Mechanical XY input and rotary encoders with touchscreen input.
- Galvanometer projection with on-screen visualisation.
- External MIDI keyboard with an on-screen keyboard.
- Raspberry Pi with the Surface itself.
- External pedals with application controls where appropriate.

The mechanical rig, including the cable spools, springs and magnetic brakes, will be developed separately and tested alongside the Surface.

### Application

The application is intended to use Python and PySide6. It should be housed in the 'Surface' directorty in repo root.

Its initial functionality:

1. On-screen MIDI keyboard emulator.
2. Touch-friendly gesture drawing area.
3. Calculation of CGL parameters from drawn circles.
4. Display of relevant CGL parameter readouts.
5. Communication with the existing Max patch.
6. Playback of sound generated by Max.

A later feature will overlay the two-ellipse curve defined by the CGL parameters on the gesture drawing area.

The application should be designed so that touchscreen XY input can eventually be replaced by mechanical XY data without requiring a rewrite of the gesture-processing or Max communication components.

## 6. Important Technical Constraints

### Existing Max patch

- Preserve the existing Max patch and its interfaces wherever possible.
- Prefer zero changes to the patch.
- Inspect existing message formats and parameter definitions before implementing communication.
- Coordinate any necessary protocol changes with Matt.

### Touch and gesture performance

- This is a musical instrument, so low latency and responsive continuous input are important.
- Preserve the timing and ordering of gesture input as far as practical.
- Avoid unnecessary processing, blocking operations and excessive redraws in input paths.
- Measure performance on the actual Surface Pro 4 rather than assuming desktop performance is representative.

### Development environment

- Primary target: Microsoft Surface Pro 4 running Windows.
- Development may take place on the Surface or another Windows machine.
- Python and PySide6 are the intended application technologies.
- Max/MSP is required for sound generation, but a Max trial is planned rather than currently assumed available.
- Keep additional dependencies and software costs low.

## 8. Current Priorities

In order:

1. Understand and preserve the existing GCS/CGL behaviour.
2. Establish reliable communication between the PySide6 application and Max.
3. Implement responsive touchscreen gesture input.
4. Implement the on-screen keyboard.
5. Display calculated CGL parameters.
6. Add the two-ellipse visualisation.
7. Evaluate the application on the Surface Pro 4 alongside the mechanical rig.

The immediate objective is a functional prototype that allows the physical interaction to be evaluated.

Do not prematurely implement the eventual Raspberry Pi, MCU, encoder or galvanometer systems.

## 9. Development Decisions for Surface App

The Surface sound milestone uses a one-way app-to-Max bridge. The Surface host keeps the existing cgsSynth CGL, mapping, and audio chain; TUIO gestures use UDP 3333 and keyboard events use OSC `/circle/note (pitch, velocity)` on UDP 3334. Max unpacks pitch and velocity into separate float inputs for the existing note manager. The Surface host disables Minilab MIDI, pad, CC, and bend inputs. No Max-to-Surface telemetry or heartbeat is part of this milestone. The app's `REQUIRE_MAX_HANDSHAKE` switch is disabled by default and can be enabled when a Max ready heartbeat is restored.
